# Dossiê: Community portal for OmniHarness, an open-source multi-agent harness for Claude Code, Codex and Hermes (github.com/ymauhn/omniharness): the public entry point of the community with a members area, a navigable library of manuals, tutorials and prompt guides, an interactive scroll-driven diagram of the framework's flow and its skills graph, and a living case study with real metrics. We want references of high-level open-source community portals, developer-tool landing pages and documentation hubs: what structure and first viewport they use, how they handle members or sign-in on static sites, how they make a library of guides navigable, which interactive diagrams or scrollytelling they use, how they show proof (benchmarks, live demos, metrics), and what people criticise about them.

## Padrões

1. **Scrollytelling sem build: passos em HTML, gráfico sticky, IntersectionObserver.** O diagrama dirigido por scroll é feito com passos em HTML, um painel fixado por position: sticky e callbacks onStepEnter/onStepProgress via IntersectionObserver, sem GSAP nem bundler; o progresso pode ser exposto como CSS custom property para que o CSS anime. Resolve o diagrama de fluxo do framework no stack HTML/CSS/JS puro do portal, com o alerta documentado de que onStepProgress é inconsistente no Safari e que CSS em viewport-height é armadilha.
   - https://github.com/russellsamora/scrollama
   - https://github.com/neon-jungle/scrollama
   - https://github.com/nateherkai/scroll-craft
   - https://x.com/basementstudio/status/1651987825598902274
   - https://x.com/MengTo/status/2086023649526452265
2. **Diagrama derivado do repositório, não desenhado à mão.** O grafo interativo é gerado a partir dos dados do próprio código (nós e arestas em JSON, renderizados em canvas com API encadeada, dagMode e onNodeClick), de modo que o diagrama não pode divergir da fonte. Resolve o skills graph com três anéis e arestas tipadas dentro da regra 'no invented claims': o mesmo TOML/JSON que o skills-graph já usa alimenta a visualização.
   - https://github.com/vasturiano/force-graph
   - https://x.com/GithubProjects/status/1996995547136512375
   - https://www.producthunt.com/products/gitdiagram-2
3. **Biblioteca navegável: sidebar da árvore, busca sempre visível, rótulos por necessidade do leitor.** Hubs de docs entregam por padrão sidebar gerada da estrutura de arquivos, busca full-text persistente, TOC, dark mode e a separação guia/referência; Diátaxis dá o eixo tutorial / how-to / explicação / referência, mas o HN avisa que quatro buckets de navegação confundem, então o rótulo funciona melhor como filtro por linha do que como seções separadas. As críticas recorrentes são SEO fraco em render runtime, customização difícil, ausência de WYSIWYG e docs 'estáticas, desatualizadas e sem vida'; a prescrição é liderar com código e navegar por intenção.
   - https://github.com/docsifyjs/docsify
   - https://news.ycombinator.com/item?id=42325011
   - https://dev.to/logrocket/starlight-vs-docusaurus-for-building-documentation-33pj
   - https://kathykorevec.substack.com/p/building-a-better-place-for-docs-197f92765409
   - https://www.producthunt.com/products/docusaurus/reviews
   - https://www.producthunt.com/products/mintlify/reviews
   - https://x.com/mintlify/status/1810826290502717480
   - https://x.com/NEARDevHub/status/1972703178413187305
4. **Membros em site estático: cifrar de verdade, delegar identidade ao GitHub, ou sair do estático com custo declarado.** Só há três formas honestas de área de membros sem servidor próprio: cifrar a página (AES via WebCrypto, senha no cliente, caveats explícitos de brute-force), usar OAuth do GitHub como única identidade (o 'membro' é quem vota/lança, sem perfil), ou pôr um proxy/Identity na frente e pagar por isso (Netlify Identity roles exige plano Business, OAuth2 Proxy exige Docker e hosting). O caso Doksy mostra o custo de um login que depende de infraestrutura fora de quota: o CTA principal morre no dia do lançamento.
   - https://github.com/robinmoisson/staticrypt
   - https://www.producthunt.com/products/devhunt-2
   - https://dev.to/stackbit/gating-content-in-jamstack-sites-40o0?comments_sort=oldest
   - https://github.com/cynthiahqy/oauth-tutorial
   - https://www.producthunt.com/products/doksy?launch=doksy
5. **Prova como leaderboard reproduzível com caveats escritos.** A seção de prova é uma tabela por harness com sucesso por tarefa (x/n), intervalo de confiança, custo em dólares, wall-clock e tokens, alimentada por resultados commitados (JSONL) e datados, com um comando de validação que prova que cada checker pode falhar; vitórias parciais e o aviso 'amostra de shakedown, não veredito' aparecem no texto, não escondidos. O anti-padrão é o superlativo sem tabela, método ou hardware.
   - https://github.com/minghinmatthewlam/openbench
   - https://aistack.imec-int.com/blog/harness-cost
   - https://x.com/firecrawl/status/2095183621086761149
   - https://dev.to/arrno/blazinglyfast-a-framework-for-belief-driven-benchmarking-1faa
   - https://x.com/MengTo/status/2086023649526452265
6. **Portal de comunidade como feed que traz de volta, com uma única porta de entrada.** Comunidades de devs open-source ganham retorno com um feed personalizado ou um fluxo de lançamento/voto, e consolidam portal + docs num único ponto de entrada quando a separação fragmenta a jornada; a crítica típica é curadoria fraca (listicles repetidos, pesos de tópico errados).
   - https://www.producthunt.com/products/daily-dev
   - https://www.producthunt.com/products/devhunt-2
   - https://x.com/NEARDevHub/status/1972703178413187305

## Lacunas

- Nenhuma referência mostra um primeiro viewport em forma de checklist operacional (o QRH da aviação); as referências lideram com código, feed ou leaderboard, não com um checklist de início de sessão, então não há prova externa de que esse viewport converte.
- Nenhuma referência combina scrollytelling com um grafo em canvas no mesmo painel sticky (scrollama e force-graph são mostrados separados); a integração passo-de-scroll -> filtro/destaque de nós do grafo precisa ser desenhada do zero.
- Nenhuma referência mostra um 'caso de estudo vivo' com métricas que se atualizam a partir do repositório numa página estática sem build; openbench tem JSONL commitado mas o leaderboard vive num site próprio, e o imec é um post fixo.
- Nenhuma referência resolve área de membros em GitHub Pages sem senha compartilhada e sem serviço pago: staticrypt é senha única e pública ao brute-force, DevHunt e Netlify dependem de backend.
- Nenhuma referência mostra uma biblioteca de 'prompt guides' como tipo de conteúdo distinto de manual/tutorial, nem como filtrá-la por host (Claude Code, Codex, Hermes).
- Nenhuma referência traz crítica de usuários a diagramas interativos de arquitetura (GitDiagram tem uma única review); o risco de o diagrama ser decorativo e não navegável fica sem evidência.
- Nenhuma referência trata o peso da página com apenas uma medida comparável ao caso sem imagens; o único número de payload (Kage, <1 MB) é de um site three.js com PNGs.
- Nenhuma referência mostra uma edição paralela em artifact do claude.ai; o padrão de publicar a mesma página em dois hospedeiros estáticos não aparece.

## Recomendações

1. Diagrama de fluxo: implementar com scrollama de cdnjs (ou IntersectionObserver direto, ~40 linhas) e painel position: sticky; expor o progresso como --sc-p em CSS e usar onStepEnter para trocar estados, evitando onStepProgress por causa do Safari e evitando alturas em vh. (Padrão: Scrollytelling sem build)
2. Skills graph: renderizar com force-graph (UMD, script tag) lendo o mesmo JSON exportado por skills_graph.py, com dagMode='radialout' para os três anéis e cor de aresta por tipo; publicar o script que gera o JSON ao lado da página para que o grafo nunca divirja do repo. (Padrão: Diagrama derivado do repositório)
3. Acoplar os dois: cada passo do scroll chama graph.nodeColor/linkVisibility para destacar o subgrafo daquele passo do fluxo; é a única composição não coberta pelas referências, então deixar um check runnable (node script que valida que todo nó citado nos passos existe no JSON). (Padrões: Scrollytelling sem build + Diagrama derivado; cobre a lacuna de integração)
4. Biblioteca: manter as linhas de dotted-rule, mas adicionar um filtro de uma linha com quatro rótulos Diátaxis (tutorial, how-to, explicação, referência) mais um por host (Claude Code, Codex, Hermes), como filtros dentro da mesma página e não como seções separadas; busca por texto sempre visível via um input que filtra as linhas em JS. (Padrão: Biblioteca navegável)
5. Se a biblioteca crescer além do que cabe numa página, servir os .md com docsify de cdnjs na mesma index.html e declarar a limitação de SEO no rodapé; não adotar Docusaurus/Starlight, que exigem build. (Padrão: Biblioteca navegável)
6. Área de membros: não criar formulário de login; oferecer duas coisas mensuráveis: (a) uma página cifrada com staticrypt para material de membros, com os caveats do README copiados na tela (brute-force possível, não é autenticação de servidor), e (b) 'membro' definido como quem tem conta no GitHub e abre issue/discussion no repo, com link direto. Registrar em docs/adr/ que Identity/OAuth2 Proxy foram descartados pelo custo e pela dependência de backend. (Padrão: Membros em site estático)
7. Seção de prova: transformar as tabelas de benchmark em formato openbench: coluna x/n por tarefa, intervalo Wilson 95%, custo em USD, data e commit do run, comando exato para reproduzir e a frase de caveat ('amostra, não veredito'); guardar os resultados como JSONL em evals/ e gerar a tabela HTML a partir dele por script, para que o caso de estudo vivo seja um re-run e não uma edição manual. (Padrão: Prova como leaderboard)
8. Publicar o peso da própria página (KB, número de requisições, tempo até interativo medido com o Playwright instalado) como uma linha do benchmark, no estilo Kage, já que o site é sem imagens; é a prova mais barata e verificável do portal. (Padrão: Prova como leaderboard)
9. Primeiro viewport: manter o checklist QRH mas seguir a prescrição 'lead with code': a primeira linha do checklist é o comando de instalação copiável e a segunda é /omniharness; tudo o mais desce. Como nenhuma referência valida o checklist como viewport, medir cliques nos dois comandos antes de investir mais nesse layout. (Padrão: Biblioteca navegável; cobre a lacuna do viewport)
10. Uma única porta de entrada: index.html roteia para biblioteca, diagrama, prova e comunidade por âncoras, sem site separado para docs; a comunidade aponta para GitHub Discussions em vez de um feed próprio, já que a curadoria fraca é a crítica dominante dos feeds. (Padrão: Portal como feed com uma porta de entrada)
