## Original OmniHarness adaptation

`checkpoint-build` is a portable orchestration skill for substantial reference-based features, refactors and migrations. It adds a routine and a compact evidence record, not another runtime or a copied commercial skill bundle.

Reuse:

- Existing TDD for behavioral seams; an independent test-design pass for reference-derived acceptance. Avoid generating a large speculative suite before the first vertical slice.
- Existing review tools or fresh native read-only reviewers. The implementer can repair findings but cannot replace either required independent verdict.
- Existing swarm/worktrees only for independent branches. Dependencies wait for accepted predecessors. Worktrees remain separate from OS containment claims.
- Existing accounting: retain every attempt and review; scope/version/unknown-value rules apply. No fixed dollar conversion or claimed resource saving.
- Existing CONTEXT/ADRs for accepted decisions. SEEN remains owned by its current consumers; old review history cannot approve changed code. Project-local feedback is retrieved selectively.

Local choices: respect standing task approval and the accepted plan; only a material scope/reference/acceptance change needs new authority. Default to two repair cycles per checkpoint unless an existing envelope is tighter. Record remaining work when no progress occurs. Visual state mismatch is `invalid`, missing evidence is `blocked`, and logic-only work can declare the visual gate `not_applicable` with its reason before implementation. An applicable gate is never skipped for missing dependencies.

The skill does not install a Stop hook, viewer, model provider or host adapter. Hook-based continuation is a separate runtime capability that must respect interruption, expiry and restart accounting. Human product acceptance remains explicit; technical completion under standing commit authority is not fabricated human approval. No settings or permission profile is changed to install this skill.
