## Run on Windows

Prerequisites: Node.js 22 or newer and the repository checkout. Terminals use PowerShell 7 (`pwsh.exe`) when it is on `PATH` and otherwise the built-in Windows PowerShell 5.1 (`powershell.exe`). In `omniforge-lab/`, run `npm ci`, then `npm start`; open the exact `http://127.0.0.1:<port>/?token=<random>` URL printed by the server. The page stores the launch token in this origin's localStorage (port-scoped) and removes it from the address bar; every API request carries it in an `X-OmniForge-Token` header and the event stream in its URL. There is no cookie: browsers send cookies to every port on 127.0.0.1, so another local service could read one. Requests whose Host is not the printed `127.0.0.1:<port>` are refused (DNS rebinding). The server binds loopback only. `npm test` runs the local store, API and real ConPTY checks. The repository-wide `scripts/check.ps1` also runs these tests.

Do **not** open `omniforge-lab/index.html` directly as a `file://` page: it has no authenticated server, `/vendor` assets or `/api/*` routes, so its controls cannot work. On September 26 the owner reported this exact mistake; a fresh synthetic demo launched from `scripts/start_omniforge_demo.ps1` returned HTTP 200 and an authenticated state with two projects, three tasks and two sessions. Its loopback URL/token and process are temporary; restart the script and open the newly printed URL instead of reusing an old address.

Add the checkout folder as a project in the interface. Project paths must already exist. App data lives in the ignored `.omniforge-lab/` directory at the repository root by default; `OMNIFORGE_DATA_DIR` can select another local folder. The store uses an exclusive lock to prevent two app processes from writing the same state. A crashed run marks previously active terminal sessions interrupted; inspect whether the recorded PID/process tree still exists before acknowledging the session in the interface. Acknowledgment records the operator's verification and permits a new session; it does not resume an old process.

For a **fresh, synthetic OmniHarness walkthrough**, run `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start_omniforge_demo.ps1` (or the same with `pwsh`) from the repository root. This creates a new `%TEMP%/omniforge-demo-*` data directory on each run and prints its exact loopback token URL; it never reuses the default `.omniforge-lab` data. The fixture has three dependent open tasks, `Build`/`Pesquisa` PTYs, two synthetic session notes (one accepted decision, one rejected quotation), and a second isolated project. No model starts. The launcher checks Node/PowerShell and Lab dependencies; its `npm ci` fallback from the tracked lockfile is untested on a missing-dependency host. [Guided acceptance](GUIDED-ACCEPTANCE.md) records the manual visual/interaction scenarios and unfilled evidence sheet.

The first real launcher smoke created the fresh fixture and bound loopback, but Ctrl+C produced `Encerramento do PTY … não confirmado` and returned exit 1 after about 15 seconds. Both recorded shell PIDs were absent on an exact read-only check, while the persisted sessions correctly remained `interrupted`. The temporary data was preserved. Stop disposable shells deliberately before quitting, inspect any uncertain session before a new attempt, and do not equate absent sampled PIDs or shell exit with all descendant cancellation. This is an observed host limitation, not a passing shutdown/recovery claim.

Current slices: projects, task dependencies, global/project/session notes with bounded retrieval, searchable repository skill metadata, a project asset inventory, three graph views backed by current local state, side-by-side PTY terminals and saved panel layout. The context brief limits both note count and serialized metadata/text to a default 4,000 characters. Asset inventory uses asynchronous directory reads and caps files, visited entries, depth and scan time; `truncated=true` signals an incomplete result. It is not a background index. Terminal commands execute **on the Windows host under the current user**, inside the selected project folder. The PTY is an interactive terminal convenience, not Docker isolation or a safe execution surface for an agent. The API is local and token-gated; a page in the same user profile could still interact with a localhost service if browser/OS protections fail. Do not expose or proxy this server to another machine.

Current Windows check: `npm test` passed **26/26**, zero skips, after the inventory, context-budget and cross-project pane fixes. The first focused invocation under the restricted command sandbox had **23/24** pass and a Unicode-PTY shutdown timeout; the same unskipped 24-test suite passed under normal host permissions before the two pane-scope tests were added. The opt-in real direct-child canary passed **1/1**: it observed a child of the selected PTY and verified that the exact child was gone before the shell reached `stopped`. In an earlier browser check, OmniHarness `Build` and `Pesquisa` PTYs displayed different canary output side by side. A project note appeared in an already-open session context after the state update; switching to a second local project hid that note and switching back restored it. Both canary shells reached `stopped` after their own stop actions. The later pane filter is covered by deterministic scope and server-module tests, but a fresh browser inspection of that final edit was blocked by automatic browser-use review. These checks cover local UI and shell behavior, not native agent confinement.

An independent Windows test exposed a narrower stop guarantee: if an intermediate child launches a grandchild and exits before the stop request, `taskkill /T` may report success after killing the PTY shell while that grandchild remains alive. The reviewer confirmed the exact orphan and then stopped only its test PID. The UI now calls this state **shell encerrado**; it does not certify all descendants. Host PTYs must not run isolated agent jobs. V1 agent cancellation requires a verified container/job boundary and a negative orphan-descendant test.

The local dashboard does not yet launch Claude or Codex, route their tool calls into the container, meter descendant tokens, provide a general coordinating chat, generate reviewed mini-tools, install as a Windows application, or complete the Goose comparison. The container worker and native bridges are separate harness code with the limitations in [T13 validation](../t13/VALIDATION.md). The [V1 release contract](V1-RELEASE-CONTRACT.md) is the acceptance checklist for these and the five agreed pillars. Screenshots of this lab establish UI behavior only; they cannot be cited as agent isolation, quality or billing evidence.

The installed `node-pty` 1.1.0 currently prints `AttachConsole failed` from a cleanup helper on Windows during `kill()`, even when the observed `onExit` and the PTY tests pass. Keep this visible as a host issue until a dependency/version or shutdown-path fix is verified; do not treat the helper message as a skipped test or silently suppress it.
