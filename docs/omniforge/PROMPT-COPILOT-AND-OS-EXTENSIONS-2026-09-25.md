# Prompt Copilot and OS extensions — design intake

Status: **owner-authorised MVP requirements; implementation incomplete**, 2026-09-25. The owner liked the current Lab aesthetic and asked for an optional active prompt companion, self-adjusting UI, richer graphs, workflows, flexible terminals, and usage/key management. The later full-MVP instruction authorised implementation of these requirements under the [V1 contract](V1-RELEASE-CONTRACT.md); it does not claim those capabilities are implemented. The ongoing E1/T13 bridge validation and the own-app/Goose comparison continue in parallel.

## Product contract

The Prompt Copilot is a small, modern robot companion next to the main prompt editor. It may observe the **local draft** while enabled, propose a clearer structure, missing project context, useful keywords/research angles and a small set of relevant installed skills/tools. It never silently rewrites or sends a draft. Every suggestion shows its source and an apply/dismiss control; a dismissal may trigger **one** concise investigative question when the intended outcome remains unclear, followed by a cooldown. It must also be possible to mute the mascot without disabling the prompt editor. Modes: Off, Discreet (on-demand or after a pause), Active (local suggestions while typing). The owner selected **Discreet as the V1 default**, with project-specific overrides, maximum suggestion count, animation preference, privacy/provider choice and latency budget. No pop-up should cover terminal input or a running task.

The owner also requested **selection-scoped assistance in the bottom orchestrator chat**, separate from idle-pause suggestions. Selecting a span with the mouse (or keyboard) offers a compact contextual action menu: clarify/rewrite this span, enrich with project context, suggest research angles, or find relevant skills/tools. The initial local menu can appear immediately; an optional semantic call follows the same provider/privacy policy as the rest of the Copilot. The menu never attaches to terminal selections. Every proposal previews the replacement or insertion against the original draft and applies only after a click, retaining undo and focus. A changed draft invalidates stale selection offsets; the test corpus includes partial words, Unicode/PT text, multiline selection, duplicate phrases, dismissal, disabled mode, terminal text selection and concurrent project switching. Track selection action outcomes separately from passive suggestions so an apparent increase in accepts cannot be manufactured by changing the trigger.

The first mascot design should reuse the Lab's existing palette and typography. Give it a compact resting state, one expressive active state and subtle motion with `prefers-reduced-motion` support; no persistent bouncing or unsolicited sound. The owner requested two skins (pixel and softly shaded modern) and a parallel [mascot design handoff](MASCOT-DESIGN-HANDOFF-2026-09-25.md) with an interactive comparison. Visual feedback does not authorize a live model call or imply that a mockup is functional.

## One catalog, progressive selection

Use the existing [skills graph](../../.agents/skills/skills-graph/SKILL.md) as the discovery layer. Ingest the installed ring and catalog ring into a versioned **metadata index**; remote proposals remain visibly unavailable. Keep `SKILL.md` as the executable instruction source, with a curated overlay for discovery fields so host-owned or third-party skills do not need mass edits. A row should contain stable `skill_id`, display name, canonical source path/URL, source hash and version, installed/catalog/remote status, supported host/OS, taxonomy domain and task intents, assertive action/inputs/outputs description, practical examples, aliases/synonyms (including Portuguese/English terms), prerequisites, authority/cost class, graph relations and a last-reviewed timestamp. Missing metadata is marked **unknown** and queued for curation rather than invented. A small relational table plus full-text index is enough initially; a graph database is not a prerequisite.

Local inventory on 2026-09-25: the current skills-graph build reports **545 nodes: 113 installed IDs, 428 catalog entries and 4 remote entries; 100 edges and 0 errors**. Its committed `docs/skills-graph/graph.json` snapshot is older, so the runtime index must be regenerated atomically and pinned by hash rather than treating that file as live truth. The scan found 114 distinct local `SKILL.md` files for 113 IDs; `graphify` has two host variants with different hashes. All 114 declare name/description, but none declares explicit synonyms, use-case examples or taxonomy. Explicit version, compatibility and license fields occur in only 17, 8 and 11 files respectively. The Lab currently lists only eight repository skills, captured at server startup, and its UI filters by substring; these are coverage gaps, not evidence that the other skills are installed in the Lab. Codex plugin-cache skills need a trusted installed-registry check before being added to the installed ring.

Canonical sidecar identity must therefore be namespaced by source and host variant, with source hash and nullable version/license; it must never merge the two `graphify` bodies under one executable ID. Curated fields cover functional summary, inputs/outputs, when to use/avoid, the five product pillars, operation/modality, PT/EN positive and negative examples, aliases, prerequisites and separately **relevance**, **availability** and **authority**. Generate an inventory with explicit gaps first, curate the eight repository skills and high-use external skills next, and finish coverage of the remaining installed IDs before claiming an exhaustive catalog. Index updates are atomic; each task pins a snapshot. Governing `AGENTS.md` and project context are mandatory context, not optional search hits.

Retrieval should first match exact names, aliases and indexed terms, then rank a small candidate set by metadata/graph compatibility, project context and installed status. The Copilot opens the body of only the chosen skill when the user accepts or an actual agent task requires it. It never loads all skill bodies into every session or suggests a catalog-only entry as already runnable. Log suggestion, accepted/dismissed status and outcome separately so selection quality can be evaluated without rewarding extra interruptions.

## Classification cascade to test, not assume

1. **Default local path:** debounced full-text/alias retrieval and deterministic eligibility rules. This has no per-keystroke network traffic and yields an inspectable baseline.
2. **Optional local classifier:** evaluate [Laya](https://github.com/NandhaKishorM/laya) as a sidecar for narrow, typed intent/skill-fit decisions. It is Apache-2.0 source and has local checkpoints, but its published 322M–421M-parameter models and CPU results are not a measured low-memory/low-latency result on this Windows host. Its own [benchmark notes](https://github.com/NandhaKishorM/laya/blob/main/BENCHMARKS.md) warn about weak zero-shot typed decisions and calibration; use held-out OmniHarness prompts in Portuguese and English before enabling automatic suggestions. Model weights and distribution license are audited separately during intake.
3. **Optional remote classifier:** [TypeSafe Jev](https://docs.typesafe.ai/introduction) accepts typed questions and returns probabilities; its [skill-selection cookbook](https://docs.typesafe.ai/cookbooks/skill_suggestion) reports fewer wrong loads on a different 182-skill roster. That result is a research pattern, not evidence of improvement here. Jev sends selected prompt context to a remote service and may consume credits, so it is opt-in per user/provider, never the default active-typing path. Send only a bounded, redacted excerpt after an idle interval or explicit request, with a visible usage source and failure fallback to the local index.
4. **Frontier host:** Claude/Codex handles complex semantic repair, investigative dialogue and proposals that need reasoning. A low-confidence classifier abstains; it does not force a skill or quietly launch a model. The existing task authority and host limits govern actual calls.

Freeze a labeled corpus with positive, negative, no-skill, ambiguous, Portuguese/English and lookalike-skill cases. Measure top-1/top-3 correctness, no-skill false positives, harmful omissions, suggestion acceptance, latency p50/p95, memory/CPU, prompts transmitted, actual token/credit coverage and user interruptions. A/B comparisons use the **same** holdout and task outcome, not only classifier confidence. No external benchmark number is imported as our gain.

The current lexical router is not yet a safe Copilot classifier: on the Portuguese query `revisar codigo antes do commit`, it ranks `setup-pre-commit` above `code-review`. Use that as an initial adversarial fixture. In addition to relevance metrics, the eligibility test must have **zero** recommendations that misstate a catalog-only, incompatible or unauthorized skill as runnable. The classifier may abstain; selecting more skills is not itself success.

## UI, workflows and multiple displays

The three graph views remain distinct. Capability nodes gain source-backed hover/focus cards with a one-sentence function, inputs/outputs, host status, short usage example, prerequisites and a link to full help. Edges animate softly on focus/selection; keyboard navigation, reduced motion and a static fallback are required. A proposed edge is styled differently from an installed/executable relation.

Add a **Workflows** view over a registry of actual saved workflows: ID/version, trigger prompt, input/output artifacts, ordered steps, referenced skills, host compatibility, scope, authority class and source. Nodes can copy a trigger prompt with success/failure feedback. A distinct **Run** action preflights dependencies, project/session identity and authority through the existing harness; a click on a diagram must not silently execute a paid or destructive flow. Suggested workflows are visible but non-executable until reviewed and installed.

Replace the two fixed PTY panes with an N-pane responsive grid and a per-window layout model. A pane binds to one session ID; output/events remain coordinator-owned. Use a configurable resource warning rather than pretending N is unbounded. To work across monitors, the same local server can serve more than one window; each window stores its own pane arrangement while task/memory/session state is shared by explicit IDs. Add bounded terminal-output replay with sequence offsets and backpressure so a second window or reconnect cannot mistake missing history for complete output. Opening another window does not duplicate a PTY process. The current host terminal's [orphan-child limitation](../experiments/omniforge-pty-descendant-2026-09-25.md) remains distinct from the isolated agent-worker gate.

## Generated UI and requested self-repair

Support two reviewable operations from the main chat: (a) assemble or rearrange **declarative** panels over declared data/actions, with preview and undo; (b) create a small tool with new logic as a versioned module/manifest in a separate worktree, test it on fixtures in a restricted preview and then explicitly enable it. The first accepted example stays the read-only broken-asset-reference checker from the [V1 contract](V1-RELEASE-CONTRACT.md). Generated code receives only scoped project data and declared capabilities, never browser access to API keys, arbitrary host shell or the coordinator ledger.

A requested auto-repair starts from an observed failure and a reproducer, builds a minimal patch in an isolated worktree, runs targeted and repository checks, shows the diff and permits activation/rollback. A crash leaves the current UI and task state usable. No automatic rewriting of authorization rules, eval fitness, provider accounting or the core application while it is serving active sessions. This retains the Helix/checkpoint workflow and avoids an overwhelming, continuously self-modifying interface.

## Usage, credits and API keys

Show separate figures for **subscription quota**, **measured run tokens**, **estimated model cost**, and **confirmed API billing**. Every figure has provider, account/session scope, source, observation timestamp, freshness and coverage. Unknown is never displayed as zero or added to a known subtotal.

Official supported observation paths are more useful than a visual scrape. The [Codex App Server](https://learn.chatgpt.com/docs/app-server) documents `account/rateLimits/read`/`updated` for ChatGPT quota windows and optional credit fields, `account/usage/read` for account token activity, and `thread/tokenUsage/updated` for a thread. The installed CLI schema confirms those method names, but a live authenticated read and event coverage remain to be tested; experimental extra fields are not a product promise. Claude Code's [status line JSON](https://code.claude.com/docs/en/statusline) can expose 5-hour/7-day used percentages and reset times after an initial response for eligible plans, while its [OpenTelemetry events](https://code.claude.com/docs/en/monitoring-usage) report per-request token categories, request IDs, duration and `query_source` including subagents. `subagent_completed.total_tokens` is the last request only and must not be summed as the whole run. The host has Claude Code 2.1.282, above the documented status-line minimum of 2.1.251; no collector is installed or certified by this design note. Its reported `cost_usd` is a client-side estimate, not a bill.

Anthropic's [Usage & Cost Admin API](https://platform.claude.com/docs/en/manage-claude/usage-cost-api) and OpenAI's [organization API usage](https://developers.openai.com/api/reference/resources/admin/subresources/organization/subresources/usage) are separate, credentialed **API billing** paths, not subscription balances. Anthropic's [third-party login guidance](https://support.claude.com/en/articles/13189465-log-in-to-your-claude-account) directs developers of tools for others to API-key authentication and forbids disguising an external app to route traffic against subscription limits. A [paused Agent SDK billing change](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan) does not settle future distribution rights. Accordingly, the existing owner-first subscription preference is valid for native Claude Code work, but the distributed OmniForge Claude integration cannot promise subscription-funded programmatic execution. **Owner decision:** V1 prioritizes a native Claude Code terminal, with a separately configured optional API-key integration. The product route must still be confirmed against current provider terms before dual-host release; the two modes have different telemetry and billing.

An API-key view stores only provider name, masked suffix, scope and last validation result in the app database. The secret belongs in Windows [Credential Management](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credwritew) or a similarly audited OS vault, referenced by opaque ID; no key in `state.json`, localStorage, graph nodes, logs, screenshots or agent context. The coordinator owns retrieval for a specifically authorized provider call, redacts output and can revoke/replace a key. Never copy host subscription credentials into Docker workers. Key entry, remote account connection, additional-charge calls and spend-limit changes each require their own consequential authorization; a telemetry read does not grant spending authority.

## Delivery order without interrupting the current checkpoint

1. Finish the in-progress T13 bridges, probe/review defects, repository battery and checkpoint commit. Keep E1 live containment/usage claims open until both hosts and descendants are demonstrated.
2. Build the metadata index and a no-network Prompt Copilot slice in the Lab: taxonomy, synonyms, examples, opt-in typing assistance, one-question rejection behavior, provenance and offline selection evals. This is the smallest useful mascot interaction.
3. Add workflow registry/diagram, graph help cards and dynamic terminal grid with multi-window replay tests. Run the own-app/Goose behavioral comparison before committing to a packaging base.
4. Trial Laya locally against the deterministic baseline, and Jev only if an owner opts in to its remote data/credit path. Add frontier semantic help after host routing/accounting is safe. A provider that cannot be measured stays optional.
5. Add reviewed generated mini-tool/self-repair preview, provider usage adapters and an OS-vault-backed key UI. Close the five-pillar V1 scenarios and clean Windows installation/recovery gates before describing the OS as complete.

Remaining nonblocking design choices: remote Jev receives a draft excerpt only by explicit per-provider opt-in; detached multi-monitor windows default to independent layouts until the owner requests synchronized layouts. These are recommended implementation defaults, not evidence that those features exist today. The owner has already selected Discreet Copilot and native Claude Code terminal plus optional API as V1 priorities.
