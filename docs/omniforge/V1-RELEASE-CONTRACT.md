# OmniForge V1 release contract

Status: **proposed acceptance contract, not a claim of release** · 2026-09-25

This contract turns the owner's approved direction into a finite first release. OmniForge is a Windows-first, locally installable agentic workspace for developers and solo founders. It should first help the owner finish real work in **OmniHarness**, then provide a reproducible demonstration for other developers. Codex is a native managed-host candidate under the owner's existing allowance. Claude's V1 default is a **native Claude Code terminal**; a managed API-key integration is optional and separately metered. Native terminal access does not itself certify OmniForge worker containment or grant a distributed product rights to subscription-backed automation. Both hosts remain in the owner-local dogfood and handoff scope, with product claims separated by verified mode. The application must remain architecturally portable, but a tested macOS/Linux installer is not a V1 gate.

V1 means one useful, verified end-to-end slice of **each** of the five pillars below. It does not mean every future workflow in those pillars is automated. A feature counts only when its runnable acceptance scenario and evidence are recorded, not when a panel or skill name merely exists.

## Release-wide hard gates

1. **Install and recover on Windows.** A developer who does not have the repository's preconfigured user profile can install, launch, update and remove the app from documented artifacts. The installer declares or provisions prerequisites, validates Claude/Codex native-login availability without copying credentials into a worker, and gives an actionable failure when a host is absent. Test the documented path in a clean Windows user or VM and record version, command, result and uninstall residue. Source checkout alone is not an installer.
2. **Two host modes, explicit boundary.** The owner-local dogfood runs an accepted task through Codex and a documented Claude Code terminal/handoff, preserving task identity, worktree and evidence. The native Claude terminal is labeled interactive host use, not a managed isolated swarm or subscription-funded product automation. A managed executor mode is certified only after a live canary proves all roles' tool-capable actions execute inside the unprivileged worker or are demonstrably unavailable, with coordinator-owned credentials/evidence, cancellation and retries. This applies to Codex and to any optional Claude API-key mode before it is advertised as managed. If a host mode cannot meet this, the product must not describe it as isolated; a process-only probe never passes this gate. A public claim of dual-host **managed** execution additionally requires a policy-compliant Claude API route and its own accepted live task.
3. **Measured execution.** Per task and host, store observed input, output and cache token categories when exposed, source receipt, child coverage, wall-clock time, active time, summed agent time, budget/allowance context, and explicit unknowns. Reconcile the native receipt with the task ledger. A failed, empty, timed-out, cancelled or incompletely attributed run cannot pass or enter a comparable cost benchmark. Do not infer billing dollars from tokens or treat an existing subscription as measured zero cost.
4. **Workspace reliability.** Two sessions can remain open side by side with independent, live terminal views, task IDs, cancellation and restart. The host PTY's `stopped` state only certifies shell exit and a request to kill the currently enumerable process tree: a real Windows [orphan-descendant counterexample](../experiments/omniforge-pty-descendant-2026-09-25.md) remains. Agent-job cancellation must use a verified container or Job Object boundary, including an orphan-grandchild negative canary, before it counts here. Concurrent writes to shared knowledge cannot silently overwrite one another. A session can resume its own project context after restart, while another project's private scope stays inaccessible. The full prescribed validation for the release candidate has zero skipped tests; visual tests run with their dependencies installed. Any accepted policy divergence is listed separately from passing checks.
5. **Reviewable delivery.** The release has a versioned build, reproducible acceptance commands, sanitized evidence index, known limitations and a visible rollback/disable path for dynamic extensions. A public demonstration shows the actual behavior on both hosts and a working community-interest path. Publishing and any private-data transfer require the owner's separate authorization; a local recording is not a public demo.

## Shared context, graphs and generated UI

The app carries project-scoped, versioned memory across its sessions. A new session retrieves a concise project/task summary and citations to underlying artifacts; it loads relevant skills on demand instead of injecting the entire library. Writes have provenance, timestamps and conflict handling. The user can inspect, correct and forget a memory item; a cross-project share is explicit. Test concurrent updates, restart, stale facts and denial of unintended cross-project retrieval.

Three related graphs remain distinguishable in storage and UI:

| Graph | Required V1 entities and check |
|---|---|
| Capability | Installed skills, catalogued candidates, host compatibility and provenance. A task query selects a minimal relevant set; an uninstalled candidate cannot execute as though installed. |
| Task | A frozen reference DAG of requirements/dependencies and a separate execution/attempt graph with agents, retries, evidence and outcome. Adding a retry or artificial branch cannot earn new requirement weight. |
| Project knowledge | Projects, sessions, assets, decisions, source files and evidence links with access scope and source/version references. A changed asset is traceable to the sessions and tasks that used it. |

For chat-adjustable UI, V1 accepts **one small tool with new logic**, not just rearranged widgets: from the main chat, generate a read-only project-asset link checker that traverses a selected project's known assets and reports broken references. It must create a reviewable versioned module/manifest and tests, run in a restricted preview against fixture assets, then be enabled or disabled without changing the core app. A malicious or crashing variant must fail closed and leave the workspace usable. The generated tool receives only the selected project's scoped data and declared actions. General self-modification and arbitrary plugin execution are outside V1.

## Evaluation and bounded evolution gate

E2 uses frozen engineering-first reference task graphs, with at least one case from each other pillar. It separates requirements from attempts, uses normalized weights with a positive floor and bounded centrality, makes critical requirements eliminatory, and penalizes **unproductive** repetition without penalizing justified verification. Offline fixtures must demonstrate critical-failure rejection, no gain from artificial splitting, no credit for a no-progress loop, and distinct wall-clock versus summed parallel agent time. Refuters are tested against planted true/false findings and human adjudication; disagreement and false negatives are reported. Coefficients are proposals until this calibration passes.

A bounded genetic **research pilot** follows, without mutating the evaluator, authority policy or hard constraints. Its search space is limited to Gauntlet subagent/lens selection, effort allocation per reference node and fallback strategy. Compare a fixed configuration, random search and genetic search on the same held-out cases with equal total evaluation budgets and repeated trials; count every candidate and failed run. Record outcome variance, quality, real token categories/coverage, wall time and summed agent time. Incomplete native accounting or isolation invalidates a cost/containment comparison. Human review decides whether any candidate is promoted; V1 requires an honest pilot report, **not** a claimed optimization gain or an autonomous production optimizer. See [ADR 0006](../adr/0006-evaluation-first-evolution.md) and [eval plan](../evals/PLAN.md).

## Critical path and release decision

The owner's new Prompt Copilot, full skills metadata, richer graph help, Workflows, flexible/multi-monitor terminals and usage/key-management requests are specified in the [design intake](PROMPT-COPILOT-AND-OS-EXTENSIONS-2026-09-25.md). They are V1 acceptance work after the current bridge checkpoint, with offline-first Copilot and explicit provider-policy/credential gates. A live subscription-quota display is distinct from a measured token ledger or confirmed API bill. The distributed Claude pathway must comply with the provider's [third-party login guidance](https://support.claude.com/en/articles/13189465-log-in-to-your-claude-account); a native Claude Code terminal and an API-key-backed product integration are separate capabilities.

1. Close the E1/T13 live boundary: native Claude/Codex tool-routing evidence, all-role containment, cancellation/recovery, receipt reconciliation, then the live controls and B8/B9 that depend on them. The existing offline probes are prerequisites, not substitutes.
2. Run the approved small own-app-versus-Goose comparison on the same scenarios in [PLAN.md](PLAN.md). Record results and choose a base; avoid building the full OS twice. The choice must preserve both hosts, scoped memory and the worker boundary.
3. Implement the chosen Windows app's multi-session terminals, shared context, three graphs and one generated mini-tool. Verify the five pillar scenarios, with OmniHarness as the first actual project.
4. Freeze E2 cases and human labels; execute the bounded evolutionary pilot only when the native metrics and isolation prerequisites hold. Build a release candidate, test a clean Windows installation, and capture a sanitized dual-host demonstration.
5. Obtain the owner's publication decision, publish the truthful demonstration and community-interest path, then verify that a new visitor can reach and use that path. A public V1 claim waits for this final gate.

For every gate, the evidence index should record the artifact, source SHA/build, host and date, exact command/scenario, pass/fail/skip counts, receipt coverage, limitations and reviewer decision. A critical failure blocks release; an unknown is a limitation or a failed certification gate, never an implicit pass. The acceptance suite and release decision are human-reviewed.

**Explicit deferrals:** paid checkout and membership billing may follow V1; the landing page must not imply purchasing works until it does. Also deferred are general-purpose generated applications, automatic changes to guardrails/fitness, production campaigns, comprehensive paper submission, all reference integrations, and certified macOS/Linux packaging. The V1 community-interest path gives a real next action while payment is deferred.
