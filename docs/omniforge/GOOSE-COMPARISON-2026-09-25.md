# Goose candidate B: documentary comparison for OmniForge V1

Date: 2026-09-25. Status: **public-source review only**. Goose was not installed, launched, authenticated, benchmarked, or used to run a model for this comparison. The local [comparison plan](PLAN.md), [candidate A Lab report](LAB.md), and [V1 release contract](V1-RELEASE-CONTRACT.md) set the same outcomes for both candidates. Documentation is evidence of a supported surface, not evidence that it meets our Windows, accounting, isolation, or quality gates on this host. No winner is selected here.

The current upstream is [aaif-goose/goose](https://github.com/aaif-goose/goose). Its desktop is Electron/React around a bundled Goose CLI and ACP server, according to [`ui/desktop/README.md`](https://github.com/aaif-goose/goose/blob/main/ui/desktop/README.md#building-notes). Goose's [custom-distribution guide](https://github.com/aaif-goose/goose/blob/main/CUSTOM_DISTROS.md#architecture-at-a-glance) distinguishes configuration/recipes, MCP extensions, desktop changes and a new UI over `goose serve`. Candidate B means a *minimally adapted distribution*, with OmniHarness contracts added explicitly; it does not mean treating every built-in Goose feature as an OmniForge acceptance result.

Provider-policy limit discovered after the desk comparison: even if Goose documents Claude ACP with an existing native login, [Anthropic's third-party login guidance](https://support.claude.com/en/articles/13189465-log-in-to-your-claude-account) directs developers distributing a product to API-key authentication and forbids routing external traffic against subscription limits by disguising the client. Goose's adapter documentation is not permission for an OmniForge distribution to promise Claude subscription-backed automation. The owner chose a native Claude Code terminal as V1 default and a separately configured optional API mode; the same distinction applies to either app base.

## The same five comparison scenarios

| Scenario from `PLAN.md` | Documented Goose starting point | Adaptation and result still to test on Windows |
|---|---|---|
| 1. Two real terminals, sessions and projects | [Desktop sessions](https://goose-docs.ai/docs/guides/sessions/session-management/) can remain active and can be opened in separate windows; each session has a working directory. [Terminal integration](https://goose-docs.ai/docs/guides/terminal-integration/) attaches Goose to an existing PowerShell, with named sessions. | These sources do not establish two independent **embedded PTYs side by side in one OmniForge window**, saved split layout, terminal/process ownership, or explicit project IDs. Test two Windows shells simultaneously, different projects, switch/restart, and verify output/context cannot cross. External PowerShell windows are a useful baseline, not a pass for the requested OS layout. |
| 2. Task-linked chat fixes a reproducible defect | The [Developer extension](https://goose-docs.ai/docs/mcp/developer-mcp/) exposes shell and file editing, and [Agent Skills](https://goose-docs.ai/docs/guides/context-engineering/using-skills/) list names/descriptions before loading matching full instructions. | Map one frozen OmniHarness ticket to a Goose session and require red test, bounded diff, checks, review and E1 task/evidence identity. Goose chat completion alone cannot set `task_pass=true`. Its Developer shell normally has current-user host privileges, so this scenario cannot be promoted to an isolated executor without the separate containment test. |
| 3. Two disjoint tasks/worktrees and integration | Goose documents [parallel subrecipes](https://goose-docs.ai/docs/tutorials/subrecipes-in-parallel/) and a [Container Use MCP workflow](https://goose-docs.ai/docs/tutorials/isolated-development-environments/) that creates git branches and containers. | Establish deterministic worktree ownership, disjoint edits, coordinator integration and receipts for every subagent/retry. The Container Use workflow is an extension, not proof that every native ACP role's built-in tool path is confined to our worker. Verify actual tool routes and host-file denial before claiming all-role isolation. |
| 4. Cancel/restart, durable state and Claude/Codex handoff | Goose documents [interrupting an in-progress task](https://goose-docs.ai/docs/guides/sessions/in-session-actions/), local SQLite [session persistence](https://goose-docs.ai/docs/guides/sessions/session-management/), and [Claude/Codex ACP providers](https://goose-docs.ai/docs/guides/acp-providers/) using existing subscriptions. | Test cancellation of the agent and descendants, uncertain execution, layout/state recovery and a handoff with separate host receipts. The ACP guide explicitly says Goose ACP sessions cannot yet fork/resume and ACP IDs can differ from Goose session IDs. A restored chat view or Goose SQLite row therefore does not prove native model-session resume or reconciled telemetry. |
| 5. Choose a skill and generate a small tool with new logic | Goose [discovers and selectively loads skills](https://goose-docs.ai/docs/guides/context-engineering/using-skills/). Its [Apps extension](https://goose-docs.ai/docs/mcp/apps-mcp/) can create/modify a single-file HTML/JS utility through chat and open it in a standalone sandboxed window. | Build the same asset-link checker against fixture assets. V1 additionally needs a versioned manifest/source/tests, selected-project data scope, reviewed backend capability, restricted preview, crash/malicious negative case and disable/revert. The Apps page documents HTML windows, not these backend authorization and release controls; measure the adaptation rather than assuming either pass or impossibility. |

## Release-gate fit beyond those scenarios

| V1 gate | Evidence and gap |
|---|---|
| Claude and Codex on existing allowances | The current [ACP guide](https://goose-docs.ai/docs/guides/acp-providers/) documents `claude-acp` and `codex-acp`, their separate npm adapters, existing native logins, and extension forwarding as MCP. Goose also documents a separate [ChatGPT Codex browser-OAuth provider](https://goose-docs.ai/docs/getting-started/providers/); it is a different route from a native Codex ACP turn. Only a real run can establish which route preserves the requested host semantics, allowed subscription use, tool coverage and usage receipts here. Deprecated [CLI pass-through providers](https://goose-docs.ai/docs/guides/cli-providers/) should not be the default adaptation. |
| Scoped shared memory and three graphs | The built-in [Memory extension](https://goose-docs.ai/docs/mcp/memory-mcp/) has project-local and user-global files, but its guide says it loads **all saved memories into every prompt** at session start. That differs from V1's bounded, cited retrieval with project/task scope, stale-version handling, concurrent-write reconciliation and explicit cross-project sharing. Goose offers [skills](https://goose-docs.ai/docs/guides/context-engineering/using-skills/) and task-oriented [extensions](https://goose-docs.ai/docs/getting-started/using-extensions/) as useful inputs; a frozen reference task DAG, separate attempt graph and sourced project graph remain OmniHarness-owned data/models until implemented and verified. Optional graph-memory MCP availability is not acceptance evidence for those three graphs. |
| Unprivileged worker and real accounting | Goose's [Developer tool](https://goose-docs.ai/docs/mcp/developer-mcp/) can execute host commands with the user's privileges; [Goose in Docker](https://goose-docs.ai/docs/tutorials/goose-in-docker/) can instead put Goose itself or **extensions** in containers. Neither documented option alone proves that ACP agent built-ins, spawned roles, retries and fallback calls are unavailable on the Windows host while credentials/evidence stay coordinator-owned. The [ACP guide](https://goose-docs.ai/docs/guides/acp-providers/) also flags differing session IDs. Goose displays [session token usage and estimated cost](https://goose-docs.ai/docs/guides/sessions/smart-context-management/), but its cost figure is explicitly not the provider bill. V1 still needs per-host/attempt/descendant input, output, cache and coverage receipts, cancellation and no false passes. Unknown categories stay unknown. |
| Clean-user Windows install and updates | Goose offers [Windows desktop downloads](https://goose-docs.ai/docs/quickstart/) and [desktop updates](https://goose-docs.ai/docs/guides/updating-goose/), which is a useful distribution head start. A branded OmniForge build must still package its Rust/ACP backend and Electron UI, adapters, harness assets and worker prerequisites, then pass clean-user install/update/uninstall tests. Upstream [`ui/desktop/README.md`](https://github.com/aaif-goose/goose/blob/main/ui/desktop/README.md#goose-desktop-app) describes the desktop build; its Windows section delegates to an existing build process and is not a tested OmniForge installer. |

The current [ACP permission mapping](https://goose-docs.ai/docs/guides/acp-providers/) is particularly important for the containment trial: Goose `auto` maps to Claude `bypassPermissions` and Codex `agent-full-access`; `approve` maps to Claude `default` and Codex `read-only`. These are host modes, not our coordinator-owned worker policy. Goose's [tool permissions](https://goose-docs.ai/docs/guides/managing-tools/tool-permissions/) can restrict Goose extensions, but we have no public-source proof that such a setting removes every ACP agent built-in tool. Treat a proposed safe configuration as an experiment and run negative host-file canaries across main agents and descendants.

## License and maintenance burden

The upstream [license is Apache-2.0](https://github.com/aaif-goose/goose/blob/main/LICENSE). The official [distribution guide](https://github.com/aaif-goose/goose/blob/main/CUSTOM_DISTROS.md#important-considerations) calls for preserving license/copyright notices, marking modifications, and avoiding a trademark implication of official endorsement. It also warns that a divergent private fork makes security and feature updates expensive; it recommends keeping customization in config, recipes or separate extensions where possible. Those are concrete distribution obligations and engineering costs, not a legal review of every transitive dependency. A Goose-based V1 would need an SBOM/license check for the final artifact.

A shallow adaptation might reuse the desktop, ACP providers, skills and Apps surface while implementing OmniHarness memory/graphs/ledger as a narrow extension. A deep change to desktop layout, native ACP tool control or accounting would touch upstream UI/backend seams and increase merge burden. Record changed upstream files and conflict/update effort during the trial; do not count an upstream feature or a conceptual adapter as completed local work.

## Small empirical trial before a base decision

Freeze one OmniHarness fixture SHA, Goose release/build SHA, candidate A SHA, Windows version, provider/adapter versions, host accounts and settings. Use the five scenarios above with the same expected outcomes, safe fixture commands and a fixed adaptation-effort allowance. Record exact run commands, time, screenshots, diff/test evidence, token receipts and missing categories separately per host. Run the dual-host containment canary and cancellation/recovery tests before any cost or safety comparison. A clean Windows user/VM must exercise the actual distribution path. Compare usability, implementation time, maintenance work and measured resources separately; no unavailable measurement receives a zero score. If either base misses a V1 hard gate, mark that gate failed or unverified and keep the selection inconclusive until the owner reviews the evidence.
