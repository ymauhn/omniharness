# Native agent tool isolation: next acceptance boundary

Date: 2026-09-25. Status: **model-free Docker process and worker-adapter acceptance; no native agent-tree acceptance**. The [current process report](../experiments/sandbox-containment-2026-09-25.json) passes 14/14 and the [coordinator worker-adapter report](../experiments/container-worker-2026-09-25.json) passes 18/18 against a disposable container. The [native attempt adapters](ACCOUNTING.md) capture process and usage evidence with offline fake CLIs. None of these results proves that a real Claude or Codex worker uses the contained process profile.

The implemented offline pieces are `harness/container_worker.py` (one owned Docker container and command ledger), `harness/codex_windows_probe.py` (a disposable native command-profile canary), and `harness/claude_tool_inventory.py` (exact `system/init` tool/MCP inventory check). Their focused offline suites passed 15/15, 15/15 and 5/5 respectively; a shared process-probe regression passed 1/1 (**36/36** focused). They are separate gates; none intercepts a model's tool calls yet. The [Codex canary](../experiments/codex-windows-probe-2026-09-25.json) on this host returned **inconclusive**: the installed CLI refused restricted read access with `unelevated` and required the elevated Windows backend. Its synthetic Codex home acquired a `.sandbox` log and `tmp/arg0`; their origin is not fully attributable, and the report refuses a host-artifact pass. No administrator setup was attempted. One synthetic Claude subscription turn timed out at 90 seconds before a final receipt; its actual token use and effective inventory remain unknown. Do not count either result as a passed isolation test.

## Shared coordinator contract

Each role, retry and candidate gets its own immutable attempt ID, pinned source SHA, worktree, container or host sandbox identity, and receipt. The coordinator retains credentials, ledger, prompts and raw evidence outside worker-visible paths. It must establish the OS boundary and effective tool inventory **before** an authenticated turn; a requested sandbox flag or model statement cannot substitute for an observed boundary. Only a verified worker worktree is writable. A timeout or crash stops the exact owned process/container identity, keeps uncertain usage unknown and never relaunches the attempt automatically. After execution, `Worktrees.audit` checks actual changes and E1 control/harness separation remains a separate live acceptance.

## Claude path

The installed Claude CLI supports [`--restricted`](https://code.claude.com/docs/en/cli-reference), a mode explicitly intended for eval harnesses on shared machines. The candidate is a fresh Claude CLI on the host using its existing `claude.ai` login, `--restricted --tools "" --strict-mcp-config`, explicit permission flags and one coordinator-owned MCP config. That MCP server exposes only a bounded worker operation interface whose commands and file changes run inside the inspected Docker container. The host CLI is trusted and keeps OAuth; the claim would concern **worker tool operations**, not the entire host process. `--bare` is not a substitute because it retains built-in command/file tools and does not load OAuth in the documented programmatic path.

Before a live claim, capture `system/init` and require exactly the expected MCP server/tools with no MCP errors. [Managed MCP policy](https://code.claude.com/docs/en/managed-mcp) can override or reject local configuration. Negative canaries must attempt host Bash/PowerShell, built-in Read/Write/Edit, Agent, WebFetch, another MCP server and `@` host-file inclusion; none may access synthetic host, source or sibling sentinels. A [Bash-only hook](https://code.claude.com/docs/en/hooks) cannot provide this boundary on Windows.

## Codex path

The current `codex exec --json` adapter has fresh-turn observed usage but no documented callback for every tool call. The [App Server](https://learn.chatgpt.com/docs/app-server) offers experimental `dynamicTools`/`item/tool/call` for a client-side Docker broker, plus `turn/interrupt` and thread usage notifications. Its configuration can disable several tool families, but the [config reference](https://learn.chatgpt.com/docs/config-file/config-reference) does not document a global allowlist that proves built-in patch/file-change tools absent. Hooks have [coverage limits](https://learn.chatgpt.com/docs/hooks). Treat a broker-only configuration as a hypothesis until effective inventory and negative host-file canaries prove it.

The [native Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox) is a second candidate for Codex. The model-free profile probe attempts synthetic worker/sibling/home/coordinator paths, but no child isolation verdict was available on this host because the restricted read profile required the elevated backend. [Permission profiles](https://learn.chatgpt.com/docs/permissions) do not compose with the legacy `--sandbox` flag currently passed by `harness/codex_exec.py`; a later adapter would need a separate explicit profile route. Profiles constrain local commands but not connectors, MCP, browser, cloud or approved escalations, each of which needs a separate control or denial. The stronger Windows `elevated` mode may require administrator-approved setup; do not silently perform that setup. An offline profile result is not a live Codex turn or subagent proof.

## Acceptance sequence

1. Prove a model-free worker boundary: exact Docker container/profile identity, one intended worktree bind mount, no secrets/socket/network, denied host and sibling sentinels, exact-ID cancellation and no automatic recovery relaunch. The current Docker process and adapter canaries satisfy this bounded disposable case; concurrent coordinators and a live agent remain untested. Probe the native Codex profile separately; this host's first attempt is inconclusive.
2. Connect **one** host at a time to the boundary and capture the effective tool inventory. Run a bounded live canary on synthetic data that edits and tests the worker while host/source/sibling paths remain inaccessible. Preserve full process, tool and usage evidence.
3. Repeat for the other host and for implementer, reviewer, refuter and retry roles. A child/subagent is a separate attributed attempt or leaves whole-tree coverage explicitly incomplete. Verify cancellation, crash, failed tool and permission-denial cases.
4. Connect E1 live controls and only then consider B8/B9 comparison. Codex observed turn/thread counters and client-estimated Claude USD are not provider billing; unavailable whole-tree or billed values stay null. Do not use an incomplete run as a calibrated benchmark.

No OmniForge OS prototype, memory service or commercial proof follows from the disposable process result alone. The owner-approved sequence remains harness/evals acceptance before the desktop comparison.
